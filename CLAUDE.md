## Что это

**Dashy** (id `dashsidian`) — плагин Obsidian, который рисует дашборд из markdown-блоков.
Конфиг — YAML внутри блока, без JavaScript и без Dataview.

- Автор: Dmitriy Yurkin (`Dimagious`), MIT, Obsidian ≥ 1.13.0, `isDesktopOnly: false`
- Полное ТЗ: `docs/SPEC.md`
- Второй плагин автора; харнесс перенесён из [`Dimagious/snipsidian`](https://github.com/Dimagious/snipsidian)
- Сборка, сканер, юнит-конфиг, e2e, ролики и релиз — у [`Dimagious/obsidian-plugin-dev-kit`](https://github.com/Dimagious/obsidian-plugin-dev-kit) (`opdk`, тег пинится в `package.json`); свои настройки — в `opdk.config.mjs`

## Имя ≠ id, и это не случайность

`name: Dashy`, `id: dashsidian`, репозиторий `dashsidian`. Расхождение намеренное.

Ревью Obsidian **заворачивает имя плагина, похожее на «Obsidian»**. Первый плагин автора
подавался как `Snipsidian` и получил отказ именно по имени; после переименования в
`Snipsy` прошёл. При этом **id остался `snipsidian`** и живёт в публичном URL
`community.obsidian.md/plugins/snipsidian` — то есть правило действует на `name`, а не
на `id`.

Отсюда схема, которую повторяем: `id` и репозиторий — `<что-то>sidian`, `name` — короткое
собственное слово. Менять `name` на что-то вроде `Dashsidian` нельзя, завернут.

Код, тесты и всё, что видит пользователь, на английском: проект целится
в международный стор. Русский — через i18n, наравне с любым следующим языком.

## Соглашения

1. **Логика живёт в `core/`.** Там нет импортов `obsidian` и обращений к DOM — поэтому
   она покрывается тестами без моков. Блоки только рисуют.
2. **Ключи блоков — только в `src/blocks/schema.json`.** Оттуда их читает и валидатор,
   и генератор скилла. Не дублировать список ключей в коде.
   Эти же наборы блок передаёт в `parseConfig(source, { root, item })` — иначе
   глобальный синоним перебьёт собственный ключ блока и значение потеряется
   молча. Проверено болезненно на `title` в heatmap, см. ADR 0004.
3. **После правки схемы — `npm run build:skill` и `npm run build:reference`.**
   CI падает на рассинхроне (`-- --check` у обоих). Из схемы собираются
   скилл для агентов (Claude Code: `SKILL.md` с процессом и `reference.md`
   с таблицами ключей; остальным секция `AGENTS.md` с обеими частями;
   процесс пишется руками в `scripts/build-skill.cjs`) и справочник блоков
   на сайте, `site/reference/`.
4. **Токены CSS объявлять на `body`, не на `:root`.** В `:root` (это `html`)
   обсидиановых переменных ещё нет; `color-mix` от них невалиден, и плашки схлопываются
   в прозрачность. Проверено болезненно.
5. **Дату собирать из `getFullYear/getMonth/getDate`.** `toISOString()` в UTC+ уводит
   локальную полночь на сутки назад.
6. **Блок обязан показать свою ошибку** через `renderDiagnostics`. Молча пустой блок —
   худший исход: конфиг мог написать агент, который отрисовку не видит.
7. **Ни одного жёсткого цвета в CSS**, кроме фолбэков внутри `var()`.
8. **Английский в коде, всегда.** Комментарии, имена тестов, сообщения коммитов.
   Проект идёт в международный стор, контрибьютор может не знать русского.
9. **Ни одной строки для пользователя мимо `t()`.** Новый текст — сперва ключ
   в `src/i18n/en.ts` (там источник правды), потом перевод в остальные четыре:
   `ru`, `de`, `fr`, `es`. Недостающий ключ падает в английский, а не в сам
   ключ, но тест требует полноты от каждого поставляемого языка: половина
   строк — диагностика, и дашборд, переходящий на английский посреди фразы,
   читается как баг. Тест проверяет и совпадение плейсхолдеров.
10. **Названия дней, месяцев и дат — из `adapters/datetime.ts`.** Там обсидиановый
    `moment`, уже настроенный на язык приложения; в каталогах им не место.
    Оттуда же первый день недели: в US и Japan неделя начинается с воскресенья.
11. **Блок не читает хранилище сам.** Снимок приходит через `BlockContext.notes()`
    и один на всю страницу: заметка рисуется дважды (редактор и режим чтения),
    так что обход на блок — это обход ×2×число блоков.
12. **Блок обязан пережить повторную отрисовку.** Он живёт как `MarkdownRenderChild`
    и перерисовывается по событиям хранилища, поэтому первым делом чистит свой
    элемент (`clearBlock`). Иначе при каждом обновлении копии копятся.
13. **Счёт с существительным — только через `tPlural`.** В русском три формы
    там, где в английском две. Число рисуется отдельно и крупно, а в каталогах
    лежит одно существительное: вынуть число из готовой фразы нельзя, из
    «осталось 11 дней» получается «осталось дней».

## Ветки и коммиты

Один пункт бэклога — одна ветка — один (или несколько) коммитов. Пункта нет —
сначала пункт, потом ветка: имя ветки обязано указывать в бэклог.

**Ветка:** `<area>/<b-nnn>-<slug>`

`area` — колонка `area` из бэклога как есть (`blocks`, `ui`, `perf`, `parse`,
`meta`, `tests`, `docs`, `i18n`). `b-nnn` — id пункта в нижнем регистре.
`slug` — одно-три слова латиницей через дефис.

```
blocks/b-003-today
parse/b-019-scoped-key-aliases
ui/b-004-periodic-folder-settings
```

- База — `master`. Это единственная долгоживущая ветка.
- Зависимая работа ветвится от предыдущей ветки, а не от `master`: `today`
  не собрался бы без починки синонимов.
- **Всё — только через PR.** В `master` не коммитим и локально в него не
  мержим, даже `--ff-only`. Готово и зелено — пуш ветки и
  `gh pr create --base master`. Мерж PR решает автор.
- **Исключение — релиз.** Коммит `chore(release): X.Y.Z` и тег делает
  `npx opdk release` (см. `/release-bump`) прямо в `master` после влитого PR:
  правило про PR касается рабочих веток, а не бампа версии.
- Сопутствующая работа (правка агентов, этого файла) может ехать в том же
  PR, если так решили; тогда в описании PR перечисляются все пункты бэклога.
- **Релиз одним PR** (решение автора, 2.2.0). Пункты релиза делаются
  параллельно, каждый на своей ветке и в своём worktree
  (`../dashsidian-wt/b-nnn`), и коммитятся локально; перед пушем их
  коммиты собираются cherry-pick'ом в одну ветку релиза
  (`meta/b-nnn-release-X.Y.Z`, пункт «пересмотр инструкций»), конфликты в
  CHANGELOG и рецептах скилла разбираются руками, сгенерированное
  пересобирается, гейты на собранной ветке. Один PR, в описании все пункты.
  Worktree с `node_modules`-симлинком на основную копию: ничего в нём не
  ставить.
- Описание PR: что сделано, результаты гейтов, чек-лист ручной проверки
  (то, что не ловят тесты: живое хранилище, узкий экран), трейлер
  `Backlog: B-nnn`. Без упоминаний ассистента, как и в коммитах.

**Коммит:** Conventional Commits, тема по-английски, до 72 символов, без точки.

```
<type>(<scope>): <what was done>

<why; what was wrong; what was decided and on what grounds — not a diff retelling>

Backlog: B-003
```

`type` — `feat fix docs refactor perf test chore`. `scope` — блок или слой
(`stats`, `today`, `heatmap`, `parse`, `settings`, `skill`, `i18n`, `git`).
Трейлер `Backlog:` — в каждом коммите, который двигает пункт.

**Чего в коммитах не бывает:**

- `.claude/brain/` — бэклог, журналы сессий и ADR. Личная память, выведена
  из индекса через `.git/info/exclude`. Не коммитим и не пушим никогда.
- Соавторства ИИ, упоминаний ассистента и ссылок на сессии — ни в теме,
  ни в теле, ни в трейлерах. Автор — разработчик.

**Пуш.** `origin` — https://github.com/Dimagious/dashsidian, дефолтная ветка
`master`. Рабочая ветка пушится ради PR; `master` меняется только мержем PR.
Пункт бэклога становится `done` с хешем, когда PR влит, не раньше.

## Maker / checker

Сложные и важные пункты гоняем через агентов из `.claude/agents/`:
`maker` пишет (в рабочее дерево, без коммитов), `checker` проверяет и сам
перезапускает все гейты. Круг повторяется до APPROVE; коммит и PR — после
вердикта и «ок» автора.

- Задача maker'у — с решённой семантикой, а не «сделай фичу»: спорные
  места решаются до запуска, иначе их решит модель.
- Смотреть, что увидит пользователь, а не только юнит: все вызовы
  изменённой функции, примеры первого запуска, подписи, легенды,
  форматирование. На B-078 checker поймал именно это.
- Каждое утверждение в README и CHANGELOG сверяется с кодом.
- Решения автора, принятые по ходу («оставляем как есть»), передаются
  checker'у явно, чтобы не всплывали находками снова.
- Отчёты checker'а — в `.claude/brain/reports/` дословно.

## Каждый релиз: пересмотр скиллов и агентов

**Привычка, не гейт.** В строке релиза в бэклоге есть пункт «пересмотр
инструкций»; `/release-bump` его не проверяет, держит его автор. Фичи выходят,
а инструкции отстают: валидатор forum-helper не знал наследования ключей
с корня блока из B-131 (B-158).

Сверять с тем, что вошло в релиз:

1. **Скилл для пользователей** (`SKILL.md` и `AGENTS.md`). Ключи собираются
   из схемы, а рецепты, примеры и «чего плагин не делает» написаны руками
   в `scripts/build-skill.cjs`. У новой фичи есть рецепт? Пример не врёт
   после изменённого поведения?
2. **Агенты** `.claude/agents/` (maker, checker): новые соглашения, слои,
   грабли, пойманные на релизе.
3. **Скиллы** `.claude/skills/`: `release-bump`, `tech-writer` в git;
   `forum-helper` (и его `validate_block.py`), `idea-scout`, `search-report`
   локальные, правятся на месте и в PR не едут.
4. **Этот файл**: «Состояние», раскладка, команды.

Итог — правка или строка в PR «пересмотрено, менять нечего» по каждому из четырёх.

## Релиз: что решает автор

Релиз делает `npx opdk release X.Y.Z` (или `patch`, `minor`, `major`; сначала
`--dry-run`): версии, `chore(release)`, аннотированный тег, workflow ядра,
публикация. Номер выбирает автор по MAJOR-правилам из начала `CHANGELOG.md`.
Версия схемы (`version` в `src/blocks/schema.json`) — своё число: по ней
настройки сравнивают установленный скилл. Новый ключ, значение, поведение или
процесс скилла — минорная цифра, правка формулировок — патч; без подъёма
установленный скилл ничего не узнает. Версия плагина в сгенерированные файлы
не зашита: заголовки несут токен `{{pluginVersion}}`, а установка в хранилище
подставляет версию запущенного плагина (`src/skill/stamp.ts`). Поэтому подъём
версии сам ничего не устаревает, пересобирать после релиза не нужно.

Удалённый или переименованный id команды — тоже MAJOR (ломает горячую клавишу
пользователя); смотреть `addCommand({ id })` в `src/app/plugin.ts`. Перед
релизом локально `npm run e2e`: в CI его нет, и только он доказывает, что
собранный бандл работает в настоящем Obsidian.

## Команды

| | |
|---|---|
| `npm test` | vitest + гейты покрытия (90/80) |
| `npm run lint` | eslint с пресетом ядра (`obsidianPlugin()`) и `--max-warnings=0` |
| `npm run typecheck` | tsc --noEmit |
| `npm run build` | `opdk build`: styles.css + main.js + проверка, что в бандле нет кода только для Node |
| `npm run build:skill` | пересобрать скилл из схемы |
| `npm run build:reference` | пересобрать справочник блоков на сайте |
| `npm run scorecard:check` | `opdk scan`: зеркало сканера community-plugins, его ESLint-конфиг по всем файлам в git (с `site/` и `design/`) и CSS через doiuse под Chromium Obsidian |
| `npm run preview` | стенд состояний блоков в браузере, в `.preview/` |
| `npm run site:check` / `readme:check` | ссылки, якоря и тире на сайте и в README |
| `npm run release:check` | `opdk release check` (версии, `versions.json`, манифест, CHANGELOG, сборка, воспроизводимость) и затем сканер, lint, typecheck, тесты, проверки скилла, справочника блоков, сайта и README |
| `npx opdk release X.Y.Z` | сам релиз: версии, коммит, тег, workflow ядра, публикация; сначала `--dry-run`. Zip больше нет |
| `npm run dev:vault` | `opdk build --vault --watch`: сборка в тестовое хранилище (`VAULT_PLUGIN` или `--vault <папка>`) |
| `npm run e2e` | собирает плагин и гонит спеки против настоящего Obsidian (через ядро); в CI не гоняется. `firstrun`, `film-phone`, `capture`, `listing-mobile` включаются переменными `FIRSTRUN`, `FILM`, `CAPTURE`, `LISTING` (ровно `1`) |
| `npm run capture` | скриншоты и ролики для README и сайта: спек `capture`, затем `opdk demo` (настройки в `opdk.config.mjs`), затем agent-hero; запускать только по слову автора |
| `npm run film:phone` | ролик с телефоном (светлый и тёмный: MP4, GIF, постер) через `opdk demo`; только по слову автора |
